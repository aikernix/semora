# 通用复核修订协议

方案预检不再仅用自由文本驱动反复重写。Reviewer 返回 findings（类别、JSON Pointer 位置、证据、验收条件），Owner 分配稳定的问题 ID，传给下一轮 Analyst 与 Reviewer。

- repair：当前能力可表达的执行错误。修订后程序比较所指执行内容；说明、标签、假设及无关字段变化不能作为修复。没有变化就停止，并记录 plan.revision.stalled。发生变化只说明值得复核，绝不自动视为语义正确。
- clarification：口径冲突或确实缺少业务定义，Owner 直接转成允许自由输入的澄清卡片，不让两侧继续猜。
- capability：必须引用公开能力清单中的已知缺口。Owner 告知限制并询问是否调整范围，不自动换指标，也不伪装成成功查询。

再次复核必须在 resolutions 中覆盖每个结构化问题 ID，附已解决/未解决与理由。缺失、重复、未知 ID 或带未解决问题的 approved 均不接受。当前轮的完整能力清单同样提供给双方，明确区分系统行数上限与用户指定 Top N，已发布指标与临时表达式，以及数据查询与逐条 AI 后处理。

已通过候选仍使用 candidate_id 交付；Reviewer、SQL 门禁及执行权限不受影响。旧客户端的字符串 issues 保持兼容，但无执行变化的方案仍会提前停止。复核最多三次的外层预算保留。

执行方案现已支持order_by和limit，可用于单源及跨源各步骤。标量表达式与AI文本分析仍未支持；这些限制被显式告知模型，避免要求它在不可表达的方案中无限修订。所有机制只使用配置、契约及当前证据，不包含固定行业规则。
