# 模型主导的表间关联分析

## 数据流与所有权

扫描全量结构 → 保存按表精简输入 → 首轮提取搜索线索 → 共享搜索与命中分组 → 批内、跨批分析 → 全局关系核查及只读验证 → 自动发布。

- `semora_meta.datasource_tables`：原始结构。
- `semora_meta.datasource_relationship_inputs`：一表一行的精简输入，字段仅 `name/type/comment`，附表说明、主外键、唯一约束。没有预生成字段别名或语义目录。
- `datasource_onboarding_jobs`：进度、统计、错误、检查点引用；不存整份表理解结果。
- `RELATIONSHIP_CHECKPOINT_DIR`：任务研究检查点和内容寻址缓存，原子写入。检查点用于恢复和诊断，不作为页面人工审核队列；终态文件七天后在后续任务启动时清理。
- `semora_meta.relationship_candidates`：持久化分析候选、证据、状态及人工审核信息。`pending/unresolved` 进入待审核；人工拒绝和停用统一为 `disabled`，人工同意和启用为 `accepted`。自动 `rejected` 仅保留诊断，不进入四状态页面。成功发布后清理未再出现的旧自动候选，人工 reviewed 和 disabled 记录始终保留。
- 单源包 `payload.relationshipRecords`：仅当前已生效关系及依据；`payload.relations` 是对应的本体映射。待审核和已停用关系不进入正式本体。
- `ontology_core.domain_cross_source_relations`：业务域的跨源关系；与业务域快照在同一事务更新。初始化从当前有效业务域配置回填，不从历史候选恢复。

源结构仍完整保存。关联输入默认排除大文本、二进制、日期时间、浮点和带小数字段；主外键、明确引用、类型限定和短字符串视图字段保留例外。

## 分批、模型请求和成本

首轮每次最多二十张详细表，只提取来源字段、问题和搜索词，允许没有线索，不输出关系。搜索仅匹配实际表名、表注释、字段名称和字段注释；不匹配 JSON 属性、内部标识和库名前缀。命中后直接使用完整精简卡片，不先往返读取目录摘要。

相同搜索与相同命中集合合并，来源表未命中仍加入对应组。每组按稳定标识分成最多二十张的批次；批内分析一次，不同批次两两组合只分析跨批表对。每次最多四十张，完整请求继续受 64 KB 字节预算约束，不能把字节数宣称为精确 token 数。超限递归拆分表对工作区域，宽表则做字段资料分片，保留所有交叉组合；任务技术未完成不得视为无关联。

各组共用完整表对覆盖记录；一次审核覆盖两表全部可用映射后，后续组不再重复。自引用允许不同字段有依据地相连，不生成同字段自恒等关系。模型不预选主表，不要求引用目标字段叫 id。三批、五批等分组数量只决定覆盖任务，不设最终关系输出上限。

`RELATIONSHIP_MODEL_CONCURRENCY` 默认 3，进程内关联建模各阶段共用并发限额。第一阶段完成后安排比较任务，任务完成即领取下一个。检查点记录阶段、任务计数、模型响应、搜索结果、未解决线索及关系结论。相同输入恢复时复用响应；协议和研究版本升级后不沿用旧完成标记。每条未解决线索最多两轮新增资料补查；无新增资料即结束探索。总调用预算默认 2000，耗尽显式失败，保留旧有效包。

不同角色引用通常对应不同字段，分别保留。相同字段映射与完整限定的反向连接共享研究，不因提议措辞不同重复审核。输入变化或新增证据才能重新研究。研究模型调用数与发现调用数分别记录。

## 成立与发布

名称相似只用于发现。审核需结合原始字段说明、约束、视图定义和匹配数据。独立复核只在目标歧义、共享主体可能冒充直接引用、编号体系不清或证据矛盾等情况触发，不接收分析员意见作为事实。明确引用且验证无冲突可按版本化策略跳过独立复核；跳过不会伪造第二份意见。全局上下文包含其他提议，但不把提议当成已证实关系。支持复合键与有原始依据的附加条件，不猜测编码转换。

采样请求多读取一行，区分恰好读满和确实截断。完整扫描的小基数集合可用于验证；空表并非反证。视图优先通过单表直接投影和底表约束推导唯一性；仍无法证明时，使用每条语句最多三秒的只读全键重复检查，并标明仅对当前数据有效。空集合不能证明唯一性；无法证明时基数使用 `unknown`，不伪造 `N:1`。

A/B 共享 C 不能单凭共享编号批准 A—B，直接引用则可独立保留。不同编号体系必须区分。旧关系即使没有重新召回也进入定向复查，不能直接清掉。

只有通过的关系进入最终包。生成过程中的技术失败保留旧包。业务域保存后新查询读取新快照，已开始查询继续使用原快照。跨源记录跟随业务域事务发布；单源更新时，对携带依赖证据的跨源记录按相关表变化定向复验。

多业务域属于独立发布事务，不提供跨服务、跨业务域的分布式原子提交。若更新中途失败，已经发布的域是完整快照；任务重试负责继续同步。历史跨源关系没有结构化依赖记录时，需要显式跨源重分析来补齐依赖证据。

## 迁移和回退

1. 备份元数据库及 Ontology 数据库，保留当前镜像、业务域快照及本体包。
2. 顺序执行 API 元数据迁移至 `013-relationship-inputs.sql`。迁移只从当前包引用的历史通过候选补全关系记录，不重新激活其他历史 accepted 项。
3. 执行新版 Ontology `/ontology migrate`，建立并回填跨源关系表；再更新 API 和前端。Compose 已挂载检查点命名卷，API 镜像创建相应非 root 可写目录。
4. 验证当前关系数量、条件、列表及编辑接口。新任务完成后检查模型调用、未生成原因和覆盖统计。
5. `scripts/retire_relationship_candidates.py --archive <备份路径>` 默认仅预览；明确加 `--apply` 后先独占创建归档文件，再清理旧候选与旧任务大块分析 JSON。此步骤不会在启动或迁移时自动执行。

保留旧 pending_count 数据库列作为回退兼容，现代接口不返回该字段。回退前如执行过旧候选清理，须从归档或数据库备份恢复旧候选，再切换旧镜像。新增输入表和检查点卷不会替代原结构；无需通过删除新表来回退。

关系列表按“全部／已生效／待审核／已停用”展示。`POST /datasources/{id}/relationships/{relation_id}/decision` 接收 `approve/reject/disable/enable`；旧 DELETE 仅作兼容停用，旧 restore 仅作兼容启用，均不再物理删除。人工停用按完整关联映射签名抑制后续重跑，重新启用后才可再次生效。

## 验证方式

`test_model_directed_discovery.py` 覆盖千表调度、检查点恢复、跨批读取、超过十二条输出、相同请求合并、完整条件、成功发布和失败保留旧包。API 全量回归与 Ontology 隔离数据库事务测试一起执行。前端通过类型检查与生产构建。

`evaluate_relationship_discovery.py --tables ...` 在独立进程中读取现有元数据与模型配置，仅调用读取视图和只读匹配验证，不迁移、不创建正式任务、不保存采样到元数据库、不发布本体。结果必须说明选择的子集、技术错误、调用量和逐条证据；合成数据结果不能宣称为生产准确率。

## 查询粒度防护

查询协议新增可选 `LogicalQueryPlan.grain_refs`、`SQLProgramStep.result_grain` 和 `metric_sources`，历史记录仍可读取。SQL AST 校验结合实际唯一键和派生表分组键识别连接放大，覆盖 COUNT、SUM、AVG；不同明细分支先分别聚合。前置 SQL 可证明的唯一键沿跨源本地步骤传递，不把抽样结果或模型声明直接当唯一性证明。仅作为存在性条件使用的分支优先使用 EXISTS；明细配对不一概禁止。粒度错误进入既有定向修复，同一步最多两次，仍失败不执行错误 SQL。静态检查不保证能证明任意 SQL 的全部业务语义。

## 任务取消与重新分析

数据源页统一将 completed、completed_with_pending、failed、cancelled 视为终态，取消状态不再显示“后台处理中”或锁住操作。

- `POST /api/v1/datasources/{id}/onboarding/{job_id}/cancel`：定向取消指定任务，终态幂等返回；停止本进程工作任务、持久化取消状态并保留已有生效包。扫描阶段同时请求执行器取消。正在发布完整结果时返回 409，避免中断发布步骤。
- `POST /api/v1/datasources/{id}/relationships/analyze`：复用已扫描结构启动新任务，重新请求模型，不复用旧任务的发现或研究结论；同一新任务中断恢复仍可使用自己的检查点。没有结构返回 409，请先扫描。有任务运行时沿用现有任务，界面引导先取消。
- 明确取消的任务不会在重启后恢复；未明确取消的进程中断仍保留原恢复策略。检查点用于恢复和诊断，不作为人工确认队列。

## 模型等待与类型识别修复

关联建模使用独立 RELATIONSHIP_NO_DELIVERY_SECONDS=300，模型单次请求总时限 LLM_TIMEOUT_SECONDS=300。计时从实际模型调用开始；排队、其他批次、补查和后续重试不共用同一个300秒计时器。重试和补查仍有次数及调用预算，不是无限循环。普通查询的60秒未交付保护保持原配置。LLM_ENABLE_THINKING 显式设为 false，向接口发送 enable_thinking=false；不自动修改该选项以适配其他供应商。

字段可比较性使用独立类型族，不要求先转换成带精度的SQL导出类型。NUMBER/numeric/decimal可识别为数值族，原类型不被伪造精度；未知类型与已知不兼容分别记录 type_unresolved/incompatible_types，跳过该提议而不是中止其他提议。复合映射整体判断，不保留半条映射。类型校验通过仍须满足引用用途和完整条件判定。

## 阈值化召回组整理（_V2）

生产主链路为“关键词提取 → 程序检索与单表过滤 → 阈值化召回组整理 → 关系发现”。程序检索仍负责生成候选表和表对；召回组不提供人工开关，也不读取环境变量决定是否整理。

表数量不超过 20 张的召回组直接进入后续关系发现，不调用整理模型；超过 20 张的召回组自动发起整理。每个整理请求只包含一个召回组，不把多个组拼进同一请求；不同组按现有三并发限额分别处理。组标识使用输入内容摘要的短前缀，减少上下文和模型输出长度。

整理协议为增量输出：程序默认保留当前组和全部命中成员，`groups` 只提交需要替换当前组布局的拆组结果，`excluded` 只提交明确误命中；没有变更时返回空数组，不逐表复述。被引用的组必须完整交代未排除成员。提示词只描述通用整理职责，不包含具体业务对象或项目专用关键词。

全流程和阶段接口仍可单独执行 `organization` 用于诊断；`discovery` 消费整理结果，不再把整理完成标记作为人工开关条件。超过20张表的召回组逐组请求模型整理，模型直接给出后续实际分析的组及每组完整成员；未输出的表自然跳过，不输出排除项，也不要求覆盖原组。整组保留时模型必须显式列出全部成员，空 `groups` 仅表示没有需要分析的组。模型输入和输出都不包含原组ID，程序在收到响应后把多个输出组统一关联到本次请求的内部原组ID。程序只校验非空成员和表ID来源，不再执行全量覆盖校验；单表组允许返回但后续过滤，空表组仍非法。字段级来源和目标映射不在整理阶段输出，由后续详细比较的 `key_pairs` 负责。版本变更为 `keyword-discovery-v17-explicit-groups`，检查点、工作缓存和生成器版本随输入指纹隔离。回归覆盖小表组跳过、大表组单请求整理、多组内部ID关联、部分表选择、整组保留、空选择、拆组、单表过滤及非法表重试。

详细比较是封闭任务，只返回 `relations`，不再通过 `keywords` 扩大召回或输出 `gaps`；大组 Agent 的主动搜索保持独立。`reason` 限制为一句、最多60个字符，无条件时省略 `guards`。比较表卡片不发送普通索引，有效唯一索引归并到唯一约束，主键去重；已由程序建立或与当前表对无关的外键不进入请求。提示词使用精简输出模板，服务端仍按Pydantic契约校验。

### 召回组整理（keyword-discovery-v9-organization）

关键词检索后、完整结构比较前增加组织阶段。相同命中集合先合并；多个小组按完整请求预算装包，由共享三并发队列整理。输入仅包含组标识、关键词、表ID、数据源ID、表名、表注释、命中字段的名称/类型/注释与命中位置，不提前装载全部字段。

模型可以保留、拆组、跨输入组合并或排除明确子串误命中/语义无关的命中项。一张表可出现在多个组；摘要不足时保留原组，不因数量多、缺主键或未看到目标删表。结构响应要求逐项覆盖每个来源组中的每张表，未知标识、遗漏、相互矛盾的保留/排除会按原输入重试，最多三次；失败保持技术未完成，不发布部分关系。

每个成功请求和每个输入组的整理结果都写入现有按任务、输入指纹隔离的工作记录；同一输入不重复调用，发现阶段新增关键词只整理新增召回证据。模型整理不写业务关系表。摘要单组超预算时不截断、不按页切开关系范围，记录summary_budget并保留完整组给后续大组Agent分页分析。API的organization结果含组、关键词、理由和逐项排除依据；旧检查点不会冒充新流程已完成，历史结果仍可读取。

完整运行顺序：关键词提取 → 程序检索过滤 → 召回组整理 → 详细结构分析 → 原有验证与发布。分阶段调用中，retrieval不调用整理模型；必须显式执行organization才能进入discovery。页面展示“整理关键词召回组”。
